## Known gap: Redis doesn't survive a WSL2 restart/reboot
Redis (WSL2 Ubuntu) has to be started manually each dev session — `wsl -d Ubuntu` into an interactive shell, then `sudo service redis-server start`, and that shell has to stay open (WSL2 auto-stops the whole VM, taking Redis with it, once nothing is keeping it resident — confirmed twice: a one-off non-interactive `wsl -d Ubuntu -- sudo service redis-server start` started it but the VM was torn down again seconds later since the command returned immediately). No `systemd`-based auto-start is configured yet. Accepted as a known limitation for now, matching this project's practice of flagging real gaps rather than silently working around them; can be fixed properly (enable `systemd` in `/etc/wsl.conf`, `systemctl enable redis-server`) if it becomes enough of a recurring friction to justify the extra setup.

This is a general improvement (peak memory now scales with the largest single company, not the whole universe), not a VM-specific hack.

## Phase 1 summary

- **Verified against real data and the real server** throughout, not just type-checked — including the full register → login → watchlist 3 companies → fetch facts flow, and all 4 of ROADMAP's Phase 1 failure cases (duplicate email, expired/tampered JWT, SQL injection, duplicate watchlist entry).

### Post-close addendum 2: auditing whether the embedding model's *documented* properties were actually true

Asked to confirm the Phase 5 Hugging Face model choice with certainty, then to fix what that turned up and verify the model satisfies the requirement completely. Two claims in the code comments turned out to be **factually wrong** - both written from assumption rather than measurement, and both now corrected with their evidence recorded inline:

- **"~90MB" model size was wrong: the cached weight file is `model_quantized.onnx`, 22.9MB.** `@xenova/transformers` defaults to the *quantized* build, which the comment never mentioned. This matters beyond pedantry, because quantization is a real accuracy tradeoff in a system whose entire output depends on similarity thresholds.
- **"Truncates around 256 tokens" was wrong: the real limit is 512.** Verified empirically rather than by reading docs - appended a distinctive tail to prefixes of known token length and found where it stopped affecting the embedding: at a 512-token prefix the tail still moved similarity (0.996725), at 522 tokens it was ignored entirely (1.000000). The 256 figure comes from sentence-transformers' `sentence_bert_config.json` `max_seq_length`, which transformers.js does not apply; the model's own config reports 512 for both `max_position_embeddings` and `model_max_length`.

**Does the model satisfy the requirement? Yes, with one quantified limitation.** Measured directly against the real code path:

- Model identity confirmed from the cached config (`sentence-transformers/all-MiniLM-L6-v2`, BertModel, 6 layers, `hidden_size` 384), not just from the string in the source.
- 384 dimensions, L2 norm exactly 1.000000 - so `cosineSimilarity`'s dot-product-only shortcut is genuinely valid, not an approximation.
- Separation is clean and comfortably clears both thresholds: a real paraphrase pair scored 0.9530 (above the 0.92 `unchanged` line), unrelated text scored 0.1826 (far below the 0.60 `modified` line), identical input 0.99999973.
- Real chunk sizes fit with large headroom: measured ~5.15 characters/token on filing prose, so `MAX_CHUNK_CHARS = 900` is only ~175 tokens against a 512-token ceiling (~2.9x margin). Nothing is being silently truncated. `MAX_CHUNK_CHARS` was deliberately **left at 900** rather than raised to fill the newly-discovered headroom - it governs semantic granularity (roughly one risk factor per chunk), not the maximum the model will physically accept, so the correct value doesn't change just because the ceiling turned out to be higher.
- **The one real limitation, now quantified**: compared the quantized weights against fp32 over real risk-factor-style sentences - quantization moves pairwise cosine similarity by up to **0.0245**. Critically, that error is *not* uniform: it collapses to 0.0011 on a genuine paraphrase pair (high-similarity region) but reaches its maximum in the 0.34-0.70 mid-range, which is exactly where the 0.60 `modified` threshold sits. This is the measured, numeric form of the "weak pairings near the 0.60 threshold" limitation already documented in the previous addendum - previously observed anecdotally, now with a number and a mechanism behind it. The 0.92 threshold is comparatively safe. Switching to fp32 (`{ quantized: false }`) would recover that precision at a cost of ~67MB and slower inference; **not done, because it is a tech-stack change and this project doesn't make those unilaterally** - recorded here as a known, available option rather than silently taken or silently ignored.

Comments corrected in [src/embeddings.ts](src/embeddings.ts) (size, quantization tradeoff with its measured magnitude, real truncation limit with the evidence) and [src/riskFactorDiff.ts](src/riskFactorDiff.ts) (the `MAX_CHUNK_CHARS` rationale, plus a new note at the threshold constants flagging the precision floor). `npx tsc --noEmit` clean; the throwaway audit script was removed afterward. No behavior changed - this addendum corrects the *documentation* and puts a measured number on a previously-qualitative limitation; it does not alter any score, diff, or classification.

  **A real bug found in `fetchWithRetry`'s actual behavior, discovered by tracing the code rather than assumed from its name**: when every retry attempt returns a persistent 5xx status, the function does **not** throw - on the final attempt, `attempt < maxRetries` is false, so the retryable-status branch is skipped and it falls through to `return response`, resolving with that last bad Response object rather than rejecting.
